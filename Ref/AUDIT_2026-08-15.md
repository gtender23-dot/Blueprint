## P1 — wrong behavior

### P1.1 Multi-look playbooks: the sim NEVER plays the Base look, and weights are ignored for variation choice
**Files:** `js/engine/formations.js` (`pickedVariation`, line ~42) vs the new multi-look feature in
`js/ui/views/creatorplaybook.js` / `js/engine/playbook.js`.
**Repro (numeric):** `offFormations = [{id:'Spread', weight:90}, {id:'Spread', weight:10, variation:'trips'}]`
→ 1,000 rolled snaps → **`Spread:trips` 1000, `Spread:base` 0.**
**Why:** `rollFormation` returns only the formation *id* (the rolled entry is thrown away), then
`pickedVariation` returns the **first** entry with a variation for that id. The pre-batch invariant
was one entry per formation; the new Builder intentionally saves several. So Base+Trips at 90/10
plays Trips on every Spread snap, and Base+Twins+Trips always plays whichever variation sits first.
**Fix (small, engine):** make `rollFormation` return the rolled *entry* (or its index) and pass that
entry's `.variation` through — `sim.js:4626-4632` is the only consumer pair. Keep the current
signature working for other callers by adding e.g. `rollFormationEntry()`.
**Also:** `validatePlaybook` allows duplicate *(id, variation)* pairs silently (only duplicate
no-variation entries warn) — worth a warning while you're in there.

### P1.2 Opening an old Auto-assigned composed play silently discards its routes
**File:** `js/ui/views/creatorplay.js` (`_lineupFromData`, line ~80).
**Repro:** seed a play `{parts:['post','corner','drag'], assigns:[{slot:null},…]}` (the *default*
shape the previous composer saved — Auto assignment ⇒ `slot:null`), open it in the Composer →
lineup shows `go, dig, checkdown, curl, go` (position defaults), message says "5 routes on Spread —
ready to save." Saving overwrites the play. The library thumbnail still draws the real routes,
so the editor and the card disagree.
**Why:** `_lineupFromData` only places a part if `assigns[i].slot` names a live formation slot;
null-slot routes are dropped, then `_ensureLineup` back-fills every receiver with defaults.
**Fix:** in `_lineupFromData`, distribute slot-less parts into open receiver slots (same auto-fill
order `renderPlayCard` uses) instead of dropping them; only fall back to defaults for receivers no
part claims. New-format plays round-trip fine (verified live: block + slant + flip survived).

### P1.3 Authored star is not guaranteed to be the starter — and its gate probe flakes red
**Files:** `js/engine/world.js` (`applyTeamStars` ~1133), `tools/star_player_probe.mjs` (in CORE).
**Repro:** run `star_player_probe` a few times — "authored DE is the top DE on the roster" fails
~1 in 5 (observed 2/6 runs). A D1 prestige-5 roster can generate a DE above a 'star'-caliber
(~87 OVR) authoring; `applyTeamStars` swaps out the *weakest* body and rebuilds the depth chart by
rating, so the named star sits at #2 and does not start — against the documented promise ("drops
each onto a generated roster as the STARTER at its spot").
**Fix options (pick one, owner call):** (a) after the swap, if a teammate at the position outrates
the star, nudge the star to (top + 1) composite so the promise holds; (b) force the star to the
front of `depthOrder` at his position instead of touching ratings; (c) weaken the promise + probe
to "top-2". Until then this probe alone makes the core gate red intermittently.
**Invariant verified:** `applyTeamStars` is called from `makeCreatorTeam` (Play Now) only; no
dynasty / world-gen / compileLeague path reads `t.stars`. The owner directive holds.

### P1.4 `creator_store_probe` hard-fails: it still asserts four creation kinds

### P1.5 `build_stamp_smoke` hard-fails: the stale-build warning no longer prints the foreign hash
**Files:** `js/ui/views/mainmenu.js:55-59` (deliberate UX change — hash moved into the tooltip,
visible text is now "⚠ update ready — reload once") vs `tools/build_stamp_smoke.mjs:82`

Fix the probe to assert the foreign hash in the `title` attribute instead.

### P1.6 Team Editor: the first click after typing in a text field is swallowed
**File:** `js/ui/views/creatorteam.js` — `#te-name`, `#te-nick`, `#te-cresttext` all wire
`change` → full `rerender()`.
**Repro (live, headless):** open Team Editor → type a team name → click "＋ Add a star" → nothing
happens (row count stays 0; a second click works). Same for Save Team right after typing.
Mechanism: mousedown on the button blurs the input → `change` fires → rerender destroys the button
mid-click → mouseup lands on a fresh node that never saw mousedown. This is the exact
"listener wired to elements a re-render removes" class flagged for this audit. The other new
editors already do it right (`#pb-name` / `#play-name` / `#def-name` are read lazily via
`_syncName()` with no change-rerender).
**Fix:** drop the `change`→`rerender` listeners on those three inputs and recompute the crest
placeholder inside the existing action handlers (all of which already call `_sync()`).

## P2 — visual / polish

1. **Formation diagrams clip the backfield at small sizes.** `renderFormationDiagram`
   (`routeart.js` ~287) uses fixed `topPad 22 / yScale 172` tuned for its 180×116 default, but the
   Builder look-cards render at 118×74, list thumbnails at 120×76 and the preview at 130×84 —
   backfield content reaches y≈95, so **QB/RB/FB are cut off on every look card** (confirmed
   on-screen: Power-I Base shows half an FB, the HB is gone; the Trips variation card loses the RB
   entirely; bounds-check found all 22 variation cards + Power-I/Jumbo/Wishbone-class base cards
   clipped). Fix: scale `yScale`/`topPad` from `o.h` (e.g. `ySpan = H - pad; sy = topPad + (y-0.46) * (H*1.48)`)
   or compute from the layout's max y.
2. **The "block bar" is invisible on play cards.** `renderPlayCard` draws the 10×5 white block
   rect at the same center as the 4.2-radius white receiver dot, and paints it in the same `dots`
   layer — white-on-white, fully covered. A blocked receiver reads as "receiver with no route,"
   which is what the overhaul was supposed to eliminate. Draw the bar wider than the dot
   (or dark-outlined, offset above the LOS).
3. **Game Plan can't distinguish multi-look entries.** After loading a multi-look book, the weight
   list shows two identical "Spread" rows (no variation badge — confirmed live: "Spread 40% /
   Spread 30% / Power-I 30%"), the header counts unique ids ("2/5 formations selected" with 3
   entries), the formation-card toggle removes only the first matching entry per click, and the
   5-formation cap counts entries rather than formations. Cosmetic until P1.1 lands, then worth a
   `· Trips` suffix on the row label.
4. **Loading a stale Workshop creation is a silent no-op / vague failure.** The Game Plan loader
   (`gameplan.js` ~2847) and both new-game appliers (`newgame.js` ~750/756, bare `catch {}`)
   call `loadCreationData` **without** `repairCreation`, so a book authored before a rename throws
   inside `apply*` and either notifies "Could not load that creation" (Game Plan) or silently does
   nothing (new game). The repair layer exists precisely for this — run it in both entrances and
   surface `changes`.
5. **Workshop hub doesn't clear sibling editor state.** `creator.js` tab clicks reset `ui.pb`/`ui.def`
   but not `ui.play`, `ui.pbPreview`, `ui.team` — e.g. leave a playbook preview open, go to the hub,
   reopen Playbook Builder and you land back in the preview rather than the list.
6. **`worldgen_check` warnings** (benign, pre-existing): 1 numeric-fallback abbr; generation
   ~2s/world in the cloud.
